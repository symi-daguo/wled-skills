# 光配方设计方法论（铁律 + WLED 能力对照）

> 这份文档存在的唯一理由：客户（王国庆）明确要求「我说的核心要点你理解后记下来」。
> 每次做新配方之前必须从头读一遍，不允许凭感觉跳过任何一步。

## 一、铁律（违反即返工，不允许交付）

| 编号 | 铁律 | 判定标准（必须给证据） |
|---|---|---|
| **R1** | **所有灯珠必须全部用上** | `/json/state` 中所有活动分段的 `start..stop` 必须无缝覆盖 `0..N`；像素回读 `leds_never_lit == []` |
| **R2** | **任何时候不能有黑色** | 效果源码里不得有 `fill(BLACK)` / 会衰减到 0 的路径；回读 `black_pixels == 0` |
| **R3** | 一轮约 **1 分钟的不同光效**，**默认无限循环** | playlist `repeat: 0`；场景总时长 ≈ 60 s |
| **R4** | 停止方式 = 用户说「结束」或 **WLED App 手动停止** | 预设可被 App 直接点选；`--stop` 能真正卸载播放列表 |
| **R5** | 颜色渲染到**最佳状态** | 段 `bri=255`，全局 `bri 200~235`，`pal` 必须由本段三色构造（不能用随机/派对调色板） |
| **R6** | 必须**分明**、有**层次感**，动画**惊艳且符合名称** | 见第二节：同一时刻画面里要有 ≥3 个可区分的颜色层次；动画必须能读出「名称描述的那个动作」 |
| **R7** | **必须丝滑：逐灯珠无台阶 + 不冻结**（不允许「一格一格往前走」「一抖一抖」） | `verify_live.py` 的 `smooth_motion`：帧间均值 ≤ 8、p95 ≤ 30、**静止帧占比 ≤ 5%**；相邻色差 `mean_adj_colour_step ≤ 60` / `p95 ≤ 110` 作为诊断项参考 |
| **R8** | **换场景不得重置正在跑的动画** | 播放列表里动画段的 `fx`、`mi`、`of`、几何、`ix`、`c1` 必须**全程恒定**，只允许变 `sx` / `bri` / `col` / `pal`（原因见下节「R8」） |

### R8：换场景不重置动画（v1.0.5 新增，海浪配方实测得来）

Shimmer 里有一段按输入变化的硬重置：

```cpp
uint16_t inputstate = (uint16_t(SEGMENT.intensity) << 8) | uint16_t(SEGMENT.custom1);
if (SEGENV.call == 0 || inputstate != SEGENV.aux1) position = -(radius << 8);
```

`ix` 或 `c1` 一变，浪尖立刻弹回起点。另有 `mi` 改变（`json.cpp:169`）、几何改变
（`FX_fcn.cpp:472`）、`fx` 改变（`FX_fcn.cpp:608`）三处 `markForReset()` 会清空 `SEGENV`。

**实测代价**：六幕各自用不同的 `ix`/`c1` 时，`verify_live.py` 在每次换场景抓到
**镜像成对的单帧跳变 349**（LED24↔65、36↔53、37↔52）；固定 `ix`、`c1` 后这些跳变全部消失。
`sx`（速度）不参与 `inputstate`，可以自由逐场景变化——这也是六幕叙事唯一可用的速度旋钮。

### R7 的根因之一：**不要自己拼色块**

早期做法是「按物理模型算出每一帧的 28 个色块，每块 2~3 颗灯」，写成 28 个 `Solid` 段。
问题不在模型，在**渲染粒度**：块内所有灯珠颜色完全相同，块与块之间（尤其浪尖处）差 200~400，
于是浪线是**跳着**走的，肉眼就是「一格一格」。
**任何「自己算颜色再切成块」的方案都必然带台阶，一律否决。**

### R7 的根因之二（更隐蔽）：**效果自身的相位是不是整数**

自己拼色块容易想到，但**原生效果也可能是整数的**。实测事故：

`gradient_base()` 里浪尖位置就是整数：

```cpp
uint16_t counter = strip.now * ((SEGMENT.speed >> 2) + 1);
uint16_t pp = (counter * SEGLEN) >> 16;      // ← pp 是 uint16，只能停在整颗灯上
val = min(abs(pp-i), ...);                    // ← 用整数距离算 blend 系数
```

于是 Gradient 的浪线**每 ~370 ms 才挪一颗灯**，其余帧完全不动 —— 客户原话「一抖一抖」。
**光看源码「有没有黑色、用不用我的颜色」是不够的，必须实测相位连续性。**

### R7 的客观判据：`motion_fraction`（探针已内置）

`probe_effect.py` 用**亮度加权质心**求浪尖的**浮点**位置（`crest_centroid`），
再看相邻帧的位移：

| 效果 | 每帧在走的比例 `motion_fraction` | 最小步长（颗） | 步长 CV | 丝滑 |
|---|---|---|---|---|
| **Gradient (fx 46)** | **22%** | 0.0 | 0.78 | ❌ 一抖一抖 |
| **Shimmer (fx 161)** | **96%** | **0.002** | 2.9 | ✅ |

- `motion_fraction > 0.85` 才算丝滑（`smooth_motion`）。
- 只看 argmax 是**测不出来的**：整数轨迹两种效果长得一样，必须用质心。

### R7 的设备级判据（`verify_live.py`，v1.0.5 起）

探针测的是「理论相位」，最终还要回读设备真实帧缓冲。判据从「相邻灯珠色差」升级为
**帧间指标**，因为「一抖一抖」是时间维度的现象：

| 指标 | 含义 | 阈值 |
|---|---|---|
| `mean_temporal_colour_step` | 单颗灯珠每帧平均走多少 | ≤ 8 |
| `p95_temporal_colour_step` | 同上 p95 | ≤ 30 |
| **`frame_stall_fraction`** | **画面与上一帧完全相同的帧占比** | **≤ 5%** |

**第三条才是关键。** 整数相位效果是「冻结几百毫秒 → 跳一整颗灯」，冻结帧的
变化量记 0，会把均值拉低。实测对照（同一台 192.168.2.9 / 70 颗）：

| 配置 | 静止帧占比 | 均值 | p95 | 判定 |
|---|---|---|---|---|
| Gradient 窄浪尖 `ix=8, sx=16` | **36.1%** | 2.36 | 12 | ❌ 冻结-跳变 |
| Gradient 宽带 `ix=120, sx=16` | — | 1.44 | 9 | ⚠️ 宽带把整颗灯的相位跳变摊薄了，数值好看但**不能当丝滑证据** |
| Shimmer + Pacifica（海浪配方） | **0.0%** | 7.4 | 24 | ✅ |

> 只看均值会得出「Gradient 2.36 比 Shimmer 7.4 更丝滑」的**错误结论**——这就是
> 必须加静止帧占比的原因。相邻色差（`mean_adj_colour_step`）保留为诊断项但不阻断判定：
> 波浪的泡沫边缘天然偏硬，判「是不是色块拼的」要看陡台阶是否**聚集在几何接缝**上。

### R7 的正解：**Shimmer (fx 161)** —— WLED 里唯一「子像素位移」的效果

`FX.cpp:5128`：（注释原文 "moves a gradient … across the strip at a given interval, up to 60 seconds"）

```cpp
uint32_t traversalDistance = (SEGLEN + 2 * radius) << 8;   // 1 pixel = 256 subpixels
int32_t  position = SEGENV.step;                            // 位置是子像素量
...
uint32_t dist = abs(position - (i << 8));                   // 子像素距离
uint8_t  blend = dist / radius;                             // 边缘线性过渡
color = SEGMENT.color_from_palette(i * 255 / SEGLEN, false, false, 0);  // 带内是「位置渐变」
SEGMENT.setPixelColor(i, color_blend(color, SEGCOLOR(1), blend));       // 向底色过渡
```

要点：
- **`position` 是子像素**（1 颗 = 256 单位）⇒ 天生不可能有整颗台阶，这是「丝滑」的物理保证。
- 带内颜色取自 **`color_from_palette(i*255/SEGLEN)`**，即**按位置取色** ⇒ 空间分层天然存在。
- 带外 = `SEGCOLOR(1)`（次色），**纯底色，永不黑**。
- 滑杆含义：`sx`=Speed、`ix`=Interval（走完一趟后的**停顿** `ix*236` ms）、`c1`=Size（带宽 `radius=(c1*SEGLEN>>7)+1`）、`c2`=Granular（调制，默认 0 关闭）、`o2`=Reverse。
- ⚠️ `c1` **必须显式给**：不写时默认 128 → `radius = 128*35>>7 + 1 = 36 > SEGLEN`，色带盖满整条。
- ⚠️ `inputstate = (ix<<8)|c1`，**改 `ix` 或 `c1` 会把 `position` 重置回起点**（浪从海平线重新出发），
  改 `col`/`pal` 则不会。做播放列表时利用这一点：想让「一层新浪从远处起」就改 `c1`。

### R7 的配套：**「逐灯珠颜色数组」`"i"` 不能用于设备端配方**

`json.cpp:314` 确实支持 `{"i":[idx,[r,g,b], idx2,[r,g,b] ...]}` 逐颗写色（`setRawPixelColor`，
不经分组/间距/2D 展开），但 `serializeSegment()`（`json.cpp:576`）**只写 3 个调色板颜色，
从不写 `"i"`**。所以 `"i"` 是**实时推流专用**：写进预设后一存就丢。
⇒ **要设备端独立循环（R3）就必须用原生效果，不能用 `"i"` 画帧。**

### R7 的杀手：`mi` / `of` 省略 = 继承上一段

`json.cpp:161` `getBoolVal(elem["mi"], seg.mirror)`、`json.cpp:172` `elem["of"] | INT32_MAX`
—— **键缺省时沿用该段当前值，不是默认值**。
实测事故：对照组探针没写 `mi`，继承了前一次探针的 `mi=true`，
于是「不对称」的对照组也报出对称误差 0.0，差点把结论定反。
⇒ **凡写 `mi`/`of` 必须每次都显式下发**（`probe_effect.apply_probe_segment()` 已强制）。

## 一·补、镜像轴法（把 1D 效果变成「涌浪推进」，而不是「转圈」）

这是解决「哪里有转圈的海浪」的**核心技术**，推导来自固件而非猜测。

### 固件事实（`FX_fcn.cpp:1671-1685`，1D slow path）

```cpp
const auto setMirroredPixel = [&](int i, uint32_t c, uint8_t o) {
  int indx = topSegment.start + i;
  if (topSegment.mirror) {
    unsigned indxM = topSegment.stop - i - 1;
    indxM += topSegment.offset;            // 镜像侧也要平移
    if (indxM >= topSegment.stop) indxM -= length;   // 环绕用的是「整条灯带长度」
    _pixels[indxM] = ...;
  }
  indx += topSegment.offset;
  if (indx >= topSegment.stop) indx -= length;
  _pixels[indx] = ...;
};
```

并且 `FX_fcn.cpp:653` / `:717`：`if (mirror) vLength = (vLength + 1) / 2;`
⇒ **开了 `mi` 的效果只计算「半条」虚拟长度**，另一半由镜像补齐。

### 结论（可直接用）

对「整环单段 `0..N`」，虚拟位置 `i` 会写到**两个**物理灯珠：

```
primary = start + i + of
mirror  = stop - 1 - i + of      （二者都按整条灯带长度环绕）
```

于是 **`of` 决定折线（镜像轴）落在哪里**。对标准的电视背光布局
（上边 `0..top_len-1` 左→右，然后右/下/左），要得到**竖轴对称**必须：

```
of = top_len / 2
```

验证（70 颗 / 上边 20 颗，`of = 10`）：配对为
`(10,9) (11,8) (12,7) … (44,45)`，正是「上边中点」与「下边中点」两处折线，
对应电视**竖直中轴**。已用 `probe_effect.py` 实测：**逐帧竖轴对称误差 0.0**（无 `mi` 时 211.8）。

### 为什么这就是「不转圈」的答案

- 开 `mi` 后效果只有 `N/2` 个虚拟位，**虚拟轴 0 → N/2 就是「海平线 → 沙滩」**：
  从上边中点出发，沿左右两边同时下行，在下边中点汇合。
- 图案左右严格对称，它的运动只能读成**「向岸边推进 / 向后退去」**，
  **不可能**读成绕屏幕转圈。
- 于是「上边=远海 / 左右=浪面 / 下边=岸」的空间规划（S4）由**几何**保证，
  而不是靠四段各写一套颜色去凑。

> 反例对照：`mi` 不开（或 `of=0`）时折线落在**对角线**上，
> 图案变成沿对角线镜像，运动是绕环的 —— 这就是之前那版「转圈的海浪」。


### R1 的已知杀手：残留分段（导致「只有一小段亮」）

WLED 的 `seg` 数组**只更新数组里列出的段**，数组下标就是段 ID
（`json.cpp`: `deserializeSegment(elem, it++, presetId)`），没列出的旧段**原样保留**。
而且**段 ID 越大层级越高**——旧段会盖在新段上面。

> 实测事故：4 段旧配方（0-20 / 20-35 / 35-55 / 55-70）残留，新写的单段 0-70 是底层，
> 结果整条 70 颗里只有 0-20 露出新效果。

**对策**：任何一次写段，都必须补齐 `{"id":N,"stop":0}` 清掉尾部
（`stop:0` 是官方删除信号，`json.cpp`: `deleted++`）。
已封装为 `apply_recipe.clear_stale_segments(ip, segments)`，**不允许绕过它直接 `seg`**。

## 二、设计流程（顺序不可颠倒）

### S1 — 先找真实参考，不要凭想象配色

需求「海浪拍打沙滩」→ 先去找**真实的海浪拍岸照片/视频**（自由授权来源，如 Wikimedia Commons）。
不允许直接凭「海是蓝的、沙是黄的」这种常识去配色。

### S2 — 分析参考素材：空间结构 + 色板 + 动作首尾帧

对着一张真实参考图要回答三个问题：

1. **空间结构**：画面上/中/下、左/右分别是什么？
   （实测参考图：上部 = 远处海面与地平线；中部 = 深蓝色浪面；中下部 = 白色浪花；前景 = 沙滩/礁石）
2. **色板**：从各区域取真实像素颜色，得到海/浪/沫/沙四组色。
3. **动作首尾帧**（关键，之前完全漏了）：
   - **首帧**：海面相对平静，远处一条白线（浪正在生成），沙滩湿暗
   - **中段**：浪涌近岸，浪面变陡、颜色转深，浪尖开始出现白沫
   - **尾帧**：浪拍碎，白沫铺开（**全周期最亮的时刻**），随后泡沫消退、水退回
   - → 首尾帧相接 = 一个可循环的周期；周期长度交给 S3 用物理算

### S3 — 按真实物理规律算速度（不允许凭手感调 sx）

- 真实**涌浪周期** T ≈ 8~14 s（风浪），拍岸取 **T = 10 s**
- 灯带绕屏幕一圈，浪「从远海推进到岸边」≈ **半圈**，即 T/2 ≈ 5 s
- ⇒ 目标线速度 **v = N / T**（颗/秒）。N=70、T=10 ⇒ **v = 7 颗/秒**（一整圈 10 s）
- 实测闭环：用 `probe_effect.py` 量出真实 `px_per_second` 与 `lap_seconds`，
  与目标比对（`verdict: ok / too-fast / too-slow`），再回头定 `sx`。
- **不许跳过测量**：「海滩运动没你测试的这么快」就是没算过的直接后果。

### S4 — 按局域网 WLED 的实际分布规划空间映射

家用 WLED 绝大多数是**电视/显示器四周一圈**（本机：`top 20 / right 15 / bottom 20 / left 15`，共 70 颗）。
「四周」必须规划成**一幅空间连贯的画面**，而不是四块各玩各的。

正确示例（海浪）：
- 上边 = 远海（最深、几乎不动，缓慢）
- 左右边 = 中间海域 / 浪面（浪经过时向下推进）
- 下边 = 岸边（浪花白沫爆发 + 沙滩暖色）

**明令禁止**：四边套四个互不相干的效果、互不相干的花色、各自乱转
—— 客户原话：「哪里有转圈的海浪」。

### S5 — 选效果（读源码确认色彩来源与是否会黑）

必须回答：这个效果**用不用我给的三个颜色**？**会不会写出黑色**？
只能用「用段色构造调色板」且「不会归零」的效果。

### S6 — 实测（探针 → 像素回读），达标才进配方

- `probe_effect.py`：单效果真实像素采样，输出 黑像素数 / 覆盖率 / 沿带色分布 / 方向 / px/s
- `verify_live.py`：整配方真实像素回读，输出 `black_pixels` / `leds_never_lit` / 画面变化
- **没有这两个脚本的实测输出，不允许说「做完了」。**

### S7 — 落配方 + 验证 + 存档

存到 `recipes/<名称>.json`，按名称可复用；结束前交还实时控制权并重新加锁。

## 三、物理速度参考表

| 场景 | 真实周期 | 说明 |
|---|---|---|
| 海浪拍岸（涌浪） | 8~14 s | 本配方取 **13.1 s**（偏慢端，客户明确说过「海滩运动没你测试的这么快」） |
| 浪碎后泡沫消退 | +3~5 s | 尾帧的余韵 |
| 节奏型灯光（呼吸） | 4~6 s | 一般「不刺眼」的下限 |
| 警示/闪烁 | < 1 s | **禁止**用于舒适类配方 |

### 三·补、`Gradient`(fx 46) 的速度是**可精确计算**的，不用试错

`gradient_base()`（`FX.cpp:1394`）里相位是：

```cpp
uint16_t counter = strip.now * ((SEGMENT.speed >> 2) + 1);   // strip.now = 毫秒
uint16_t pp = (counter * SEGLEN) >> 16;                      // 0..SEGLEN，越界即回绕
```

`counter` 走完 65536 刚好让 `pp` 从 0 扫到 SEGLEN 再回绕，所以：

```
一趟（海平线 → 沙滩）= 65536 / ((sx >> 2) + 1)  毫秒
```

**70 颗 / 上边 20 颗 / `mi+of=10`（虚拟段长 35）实测对照（`crest_lap_seconds`）：**

| sx | `sx>>2`+1 | 理论一趟 | 实测一趟 | 实测浪尖速度 |
|---|---|---|---|---|
| 16 | 5 | 13.1 s | **13.0 s** | 2.70 颗/秒 |
| 20 | 6 | 10.9 s | 11.1 s | 3.15 颗/秒 |
| 24 | 7 | 9.4 s | 9.2 s | 3.82 颗/秒 |
| 32 | 8 | 8.2 s | 7.3 s | 4.81 颗/秒 |

⇒ **`sx = 16~19` 就是 13.1 s 的真实涌浪周期**，且 `sx` 只能按 4 的档位跳（`sx>>2`），
所以别用「凭感觉微调 1~2」的方式找速度，直接按表选档。

### 三·补二、`ix` 是**浪线宽度**，不是「强度」

```cpp
int brd = 1 + loading ? SEGMENT.intensity/2 : SEGMENT.intensity/4;   // C++ 优先级：先算 1+loading
```

`1 + loading` 恒为真 → 实际取 **`brd = ix / 2`**。`brd` 是「离浪尖多远之后完全显示底色」：

| ix | brd | 效果 |
|---|---|---|
| 1 | 0 | `brd > val` 恒假 → val=255 → **浪线消失，整条只剩底色** |
| 8 | 4 | 窄而锐利的浪线（9 颗内走完过渡） |
| 12 | 6 | 自然的浪线 + 一条中间色晕带（**推荐**） |
| 16 | 8 | 宽浪线（效果默认值） |
| 200 | 100 | 过渡撑满整段 → **整条近乎纯白**（实测事故） |

> 实测事故：`ix=200` 时虚拟轴剖面是 `#EAFBFF #E7F9FE #D9F1FA…` 全是白，
> 深蓝底色完全被冲掉。原因就是 `brd=100 > |pp-i| 最大 17`，blend 系数永远很小。
> **别把 `ix` 当「强度」往大拧。**

## 四、WLED 机制速查（学自官方文档，文档已存 `references/wled-official/`）

### 4.1 分段与层级
- `seg` 数组只更新列出的段，**数组下标 = 段 ID**；删段靠 `{"stop":0}`
- **段 ID 越大层级越高**；v16.0 起支持真正的**分层叠加**，每段一个混合模式
- 混合模式字段 **`bm`**（`json.cpp:312` `getVal(elem["bm"], seg.blendMode)`），取值：
  `0 top / 1 bottom / 2 add / 3 subtract / 4 difference / 5 average / 6 multiply / 7 divide /
  8 lighten / 9 darken / 10 screen / 11 overlay / 12 hardlight / 13 softlight / 14 dodge / 15 burn / 16 stencil`
- **`of` 偏移**：把效果起点沿段平移并**环绕**——做「波沿灯带推进」的原生手段
- `grp` 分组 / `spc` 间隔：N 颗物理灯合成 1 颗虚拟灯，可让效果铺满整条

### 4.2 调色板（官方文档原文）
| ID | 名称 | 说明 |
|---|---|---|
| 0 | Default | 自动，多数效果 = 主色（**效果相关，可能被替换，绝不可用于要锁死颜色的配方**） |
| 2 | Color 1 | 只用主色 |
| 3 | Colors 1&2 | 主色 + 次色 |
| 4 | Color Gradient | **所有段色的混合渐变** |
| 5 | Colors Only | 主色 / 次色 / 三色 三段分明，对比强 |
| 1 | Random Cycle | 随机换板 —— **禁止** |
| 22 | Beach | 内置「沙滩」调色板（不同深浅的浅蓝） |
| 51 | Atlantica | 海洋绿蓝 |

> 内置占 0~71；用户自定义 72~200（`/palette{N}.json` → 运行期 ID `200-N`，**需重启才可见**）。

### 4.3 播放列表（官方语义 + 源码）
- `{"playlist":{"ps":[...],"dur":[...],"transition":[...],"repeat":N,"end":x}}`
- **`dur` / `transition` 单位是十分之一秒**（源码 ×100）
- **`repeat: 0` = 无限循环**（`playlist.cpp`: `playlistRepeat == 0: endless loop`）；`repeat>=1` 会自己停
- `transition` 是**交叉淡入**，场景之间不会出现黑帧
- 预设上限 250；`{"psave":N,"n":"名称","ib":true,"sb":true}` 保存；
  `ib` = 含亮度，`sb` = 含段边界

### 4.4 实时 / 同步 / 回读
- **实时优先级**：`{"lor":2}` = 丢弃所有外部实时包，让设备跑自己的效果；
  `{"lor":0}` 交还。仅 `{"live":false}` 在外部队列持续推送时**0.25 s 内就被抢回**
- 同步需要**两道闸门**同时开：配置 `if.sync.send.en` + 运行期 `state.udpn.send`
- **实时回读（Peek，官方文档确认）**：WebSocket `ws://IP/ws` 发 `{"lv":true}`，
  二进制帧 = `'L'` + 版本(1=灯带/2=矩阵) + 每灯 3 字节 RGB，最快 40 ms 一帧；
  同一时刻只服务一个客户端。这正是 `verify_live.py` / `probe_effect.py` 的依据。
- 写入预设/播放列表必须在**非实时模式**下进行（`wled.cpp:131` 实时态会跳过 `handlePresets()`）

### 4.5 客户自定义颜色必须真的被用上
`Segment::color_from_palette()` 在 `palette == 0` 且 `mcol < 3` 时**直接返回段色**，
否则走 `_currentPalette`。所以：
- 想让配色可控 ⇒ **`pal` 必须显式设为 2/3/4/5**，不能用 `pal: 0`
