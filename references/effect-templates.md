## 模版零：通用配方骨架（所有 playlist 配方都从这开始）

```json
{
  "name": "<配方名>",
  "type": "playlist",
  "bri": 220,
  "preset_base": 110,
  "playlist_preset_id": 150,
  "loop": { "repeat": 0, "transition": 15 },
  "stop": { "on": false },
  "_design": { "...": "把推导过程写在这里，便于下次复用与追溯" },
  "scenes": [ { "name": "...", "duration": 100, "segments": [ ... ] } ]
}
```

| 字段 | 为什么是这个值 |
|---|---|
| `loop.repeat: 0` | **0 = 无限循环**（`playlist.cpp`）。写 `>=1` 会自己停，违反 R3 |
| `loop.transition: 15` | 1.5 s **交叉淡入**（单位：十分之一秒）。它保证场景之间**没有黑帧**，是 R2 的关键 |
| `duration: 100` | 10 s 一个场景，6 个场景 = 60 s ≈ R3 的「一轮约 1 分钟」 |
| `preset_base / playlist_preset_id` | 场景预设 110..115、播放列表 150。别和已存在的预设撞号（先读 `/presets.json`） |
| `bri: 220` | 全局亮度落在 R5 要求的 200~235 |
| `stop: {"on": false}` | `--stop` 用它卸载播放列表（`if (!presetId && currentPlaylist>=0) unloadPlaylist()`） |

**每段都必须显式给的键**（缺省 = 继承该段旧值，不是默认值）：
`mi`、`of`、`bm`、`c1/c2/c3`、`o1/o2/o3`。

### 手写 HTTP 时的两个必备细节

1. **POST `/json/state` 必须带 `Content-Type: application/json`**，否则本固件会**静默忽略整个 body**
   （返回空、不报错、状态不变）。实测：不带头的 `curl -d '{"on":true,...}'` 全部无效，
   加上 `-H "Content-Type: application/json"` 立刻生效。脚本里由 `apply_recipe.py` 统一处理，手测别踩。
2. **`/json/presets`（GET）在本固件未实现**（返回 `{"error":4}` = `ERR_NOT_IMPL`）。
   枚举预设要下载 `http://<ip>/presets.json`（二进制目录解析成 JSON）。

### ⚠️ `apply_recipe.py` 的防闪钳位（v1.0.5 起按效果区分，且不再静默）

老版本有一个全局静默钳位：`sx` 钳到 `[50, 90]`、`ix` 钳到 `[80, 120]`。
**它会把按物理推导出来的参数悄悄改掉**，实测症状是本模版写进去的
seg1 `ix:0 → 80`（Shimmer 的 `ix` 是「停顿」，80 等于强制 18.9 秒空档）、
`sx:112/140/152 → 90`（六幕速度叙事被压成 55~90）。

根因是**同一个滑杆 id 在不同效果里含义不同**：

| fx | `sx` 实义 | `ix` 实义 |
|---|---|---|
| 161 Shimmer | Speed，`一趟 = 200+(255-sx)*80` ms，**越大越快** | Interval，**跑完一趟后的停顿 = ix*236 ms**，0 = 不停顿 |
| 101 Pacifica | Speed | **"Angle"，空间频率**（`waveangle += (120+ix)*i`） |
| 其他多数效果 | Speed | Intensity |

修法（已实现）：`_EFFECT_AXIS_EXEMPT` 给这两个效果各自放行 ——
Shimmer `sx∈[40,200] ix∈[0,120]`、Pacifica `sx∈[20,200] ix∈[100,200]`；
**任何真正被改写的值都会出现在返回结果的 `clamp_warnings` 里**（空数组 = 按原文写入）。
Shimmer 是子像素位移、Pacifica 是连续噪声场，都不可能频闪，防闪钳位对它们本就不适用。

> **验收习惯**：`apply_recipe.py` 之后一定回读 `/presets.json`，逐条比对
> `sx`/`ix` 是否等于配方原文 —— 只看返回的 `success: true` 是不够的。

## 模版一：方向性自然现象（海浪拍岸 / 潮汐 / 瀑布 / 风吹麦浪）

**适用**：现象有明确方向（从远到近、从上到下），且客户明确禁止「转圈」。

```json
{
  "name": "海浪拍打沙滩",
  "type": "playlist",
  "bri": 220,
  "preset_base": 110,
  "playlist_preset_id": 150,
  "loop": { "repeat": 0, "transition": 15 },
  "scenes": [
    {
      "name": "浪涌推进",
      "duration": 100,
      "segments": [
        { "start": 0, "stop": 70, "fx": 101, "sx": 60, "ix": 135, "pal": 5, "bri": 165,
          "mi": true, "of": 10,
          "col": [[47,182,216],[23,137,200],[14,92,130]] },

        { "start": 0, "stop": 70, "fx": 161, "sx": 112, "ix": 0, "pal": 2, "bri": 230,
          "mi": true, "of": 10, "bm": 10, "c1": 22, "c2": 0, "o2": false,
          "col": [[234,251,255],[0,0,0],[234,251,255]] }
      ]
    }
  ]
}
```

> **上下游六个场景只允许变 `sx` / `bri` / `col` / `pal`。`fx`、`mi`、`of`、几何、`ix`、`c1` 必须全程恒定。**
> 这是本模版最重要的一条，理由见下面「换场景不重置浪尖」。

### 三个关键参数，逐个解释

| 参数 | 值 | 推导与证据 |
|---|---|---|
| **`mi: true` + `of: 10`** | 折线落在电视竖轴 | `mi` 让效果只算半个虚拟段，`of` 决定折线位置（`FX_fcn.cpp:1671`）。`of = 上边灯珠数 / 2 = 20/2 = 10` ⇒ 折线在 LED 9/10（上边中点）与 LED 44/45（下边中点）。**实测逐帧竖轴对称误差 0.0**（不开 mi 时 211.8）⇒ 运动只能读成「向岸边推进」，不可能转圈 |
| **`fx: 161`（Shimmer）做浪线** | 子像素位移 | `position` 单位是 1/256 颗。**实测静止帧占比 0.0%**、每帧都在走 ⇒ 丝滑 |
| **`sx` 决定浪速** | 可见行程 6.0~11.6 s | Shimmer 一趟 = `200 + (255-sx)*80` ms，覆盖 `(35+2*7)=49` 个虚拟位，海平线→沙滩的可见行程占 `35/49`。sx=52→12.0 s、85→9.9 s、112→8.3 s、140→6.7 s、152→6.0 s，全部落在真实碎浪间隔 6~12 s 内（客户明确说过「海滩运动没你测试的这么快」） |

### ⭐ 换场景不重置浪尖（本模版的核心约束）

Shimmer 源码里有一个**按输入变化的硬重置**：

```cpp
uint16_t inputstate = (uint16_t(SEGMENT.intensity) << 8) | uint16_t(SEGMENT.custom1);
if (SEGENV.call == 0 || inputstate != SEGENV.aux1) {
  position = -(radius << 8);      // 浪尖瞬间弹回海平线
}
```

也就是说 **`ix`（Interval）或 `c1`（Size）只要一变，浪尖就瞬移**。除此之外还有四处会 `markForReset()`
（清空 `SEGENV`，同样让效果从头开始）：

| 触发点 | 源码位置 |
|---|---|
| `mi` 改变 | `json.cpp:169` `if (seg.mirror != mirror) seg.markForReset();` |
| 分段几何改变（start/stop/grp/spc/of） | `FX_fcn.cpp:472` |
| `fx` 改变 | `FX_fcn.cpp:608`（在 `setMode()` 尾部的默认值分支里，条件为 `_mode != fx`） |
| 整条重置 | `FX_fcn.cpp:1810` `resetSegments()` |

**实测代价**（未约束前的旧版配方）：六个场景的 `ix`、`c1` 各不相同 ⇒ 每次换场景浪尖弹回，
`verify_live.py` 抓到换场景处**镜像成对的单帧跳变 349**（LED24↔65、36↔53、37↔52 —— 成对出现正好证明是 Shimmer 层）。
把 `ix`、`c1` 固定后，这些跳变全部消失，且 `sx`（速度）不影响 `inputstate`，可以自由逐场景变化。

> 代价：**浪带宽窄不能逐场景变化**（`c1` 必须恒定）。这是「丝滑」换来的，值得。
> 「泡沫铺开」这一层改由海体层（Pacifica 的白冠 + 变白的配色）承担，人眼看仍然是「浪碎了铺开」。

> ⚠️ 上一版本文档写过「改 `ix`/`c1` 重置浪尖正好做成一幕一浪，放心用」——**已被实测证伪**，那是可见的错帧跳变，不是效果。

### 分层与「永不黑」

- **底层 `seg0` = `fx:101` Pacifica**：4 层光叠加 + 白冠，天然多色层次（满足 R6 的 ≥3 个颜色层次），自己不会写出黑色。
- **上层 `seg1` = `fx:161` Shimmer，`bm: 10`（screen）**，且它的 `col[1]`（= `SEGCOLOR(1)`，Shimmer 的底色）**故意设为纯黑**。`_screen` 对黑色是**恒等变换**（`255-(255-a)(255-0)/255 = a`），所以底色不贡献任何亮度，只把白沫按屏幕方式叠上去。
- **为什么用 screen 而不是 add**：`bm=2` 是 `color_add(t,b,true)`（相加后按比例保留色比），在太平洋白冠 + 浪线同时亮的地方会**饱和削顶**，削顶边界就是硬台阶；screen 恒 ≤255，不削顶，实测台阶更小。
- ⇒ 最终画面 = 海体 + 白浪，**任一层单独看可能有黑，合成后永不黑**（R2 由分层保证）。

> ⚠️ **不要**因为看到 `col[1]` 是黑就以为违规：黑的是「叠加层的中性底」，
> 判据是回读**最终帧缓冲**的 `black_pixels == 0`（`verify_live.py` 测的就是最终帧）。

### 60 s 循环的编排（本模版实际用的 6 幕，已验证通过）

`ix = 0`、`c1 = 22` 全程恒定（`radius = (22*35>>7)+1 = 7` 颗），只有 `sx` 与 `bri` / 配色在变：

| # | 名称 | seg0 海体（Pacifica） | seg1 浪线（Shimmer，ix=0 c1=22） | 可见行程 | 意图 |
|---|---|---|---|---|---|
| 1 | 深海微澜 | sx=40, ix=126, bri=145 | sx=55, bri=165 | 11.6 s | 浪缓，海面沉 |
| 2 | 起浪 | sx=50, ix=130, bri=155 | sx=85, bri=205 | 9.9 s | 浪线显形 |
| 3 | 浪涌推进 | sx=60, ix=135, bri=165 | sx=112, bri=230 | 8.3 s | 连续浪列推进 |
| 4 | 拍岸 | sx=72, ix=142, bri=175 | sx=140, bri=255 | 6.7 s | 最快最亮 = 浪碎 |
| 5 | 泡沫铺开 | sx=80, ix=150, bri=188（配色变白） | sx=152, bri=255 | 6.0 s | 海体白冠爆开 = 泡沫 |
| 6 | 水退归静 | sx=38, ix=124, bri=150 | sx=52, bri=160 | 12.0 s | 拉长，回到起点 |

**实测结论**（参数按原文写入设备、非钳位版本）：`verify_live.py --seconds 78` ⇒
黑像素 0 / 覆盖 70-70 / 画面变化率 100% / 静止帧占比 **0.0%** /
帧间丝滑度 均值 7.11、p95 22 / 最陡帧间跳变 135（发生在场景中间，是 Pacifica 白冠破裂）/
预设按 110→115 循环。

### 滑杆含义速查（Shimmer fx 161）

| 键 | 标签 | 作用 | 换场景可否变 |
|---|---|---|---|
| `sx` | Speed | 一趟时长 = `200 + (255-sx)*80` ms | ✅ 可以（只改速度） |
| `ix` | Interval | 跑完一趟后的**停顿** = `ix * 236` ms；**0 = 不停顿，连续浪列** | ❌ 会重置 |
| `c1` | Size | 带宽 `radius = (c1*SEGLEN>>7)+1`。**必须显式给**，缺省 128 → radius 36 > 段长，色带盖满整条 | ❌ 会重置 |
| `c2` | Granular | 调制器，**默认 0 关闭**（>0 会叠斑马纹/柏林噪声） | ✅ 不参与 `inputstate` |
| `c3` | Flow | 调制器的时间流速 | ✅ 不参与 `inputstate` |
| `o1` | Zebra | 调制器改用正弦斑马纹（默认柏林噪声） | ✅ |
| `o2` | Reverse | true 会把 `position` 反向（浪从岸边退回海平线） | ✅ |
| `o3` | Sporadic | 顿顿时长随机化 | ✅ |

### ⭐ 判「丝滑」的对照实验（别只看均值）

同一台设备（192.168.2.9 / 70 颗）、同一个 `verify_live.py`，只换效果：

看着比真·丝滑的 7.4 还「好」。所以判据必须是 **静止帧占比 ≤ 5% 且 均值 ≤ 8 且 p95 ≤ 30** 三条同时满足。

> 看 `每帧在走 …%`；设备级用 `verify_live.py --seconds 24 --no-state` 看 `静止帧占比`。

## 附：两个必须记住的判据（2026-11-26，客户当场指出"太阳固定不动"）

### 1. `Sunrise`(104) 只变亮、不移动 —— 不能用来做"太阳升起在走"

`FX.cpp` `mode_sunrise()` 把同一颜色镜像写到 `i` 与 `SEGLEN-1-i`：

```cpp
SEGMENT.setPixelColor(i, c);
SEGMENT.setPixelColor(SEGLEN - i - 1, c);
```

亮区**恒在中点向外扩**，随时间只变亮。实测平均亮度 41 → 175（看起来很"有效果"），
但客户看到的是"太阳固定在一个区域"。要"会走"必须换原语。

### 2. 只量平均亮度会漏掉"变亮但不动" —— 必须量**变化质心**

- 亮度质心：静态亮底会把质心摊平（双层里底层 Sunrise 一亮，位移只剩 0.05）。
- **变化质心**：逐帧 `|本帧-上帧|` 的分布质心，跟着"正在变的那个东西"走。
  实测双层日出 0.00 → 0.21 → 0.27 → 0.44 → 0.55 → 0.86 → 0.17，一圈约 10 秒。

判据：`scripts/verify_motion.py --ip <ip> --seconds 12`，两个位移任一 ≥0.35 即"在动"。

### 3. "既亮又会走"单效果做不到 —— 用分层

| 单效果 | 结果 |
|---|---|
| `Sunrise`(104) | 亮，但不动 |
| `Meteor`(76) `ix=190` | 会走，但只亮 5% 灯珠（平均亮度 8–12） |
| `Meteor`(76) `ix=255` | 亮了（75–83），拖尾铺满整条 ⇒ **又不动了**（0.09） |

**正解：`seg0 = Sunrise`（天亮，bri 170）+ `seg1 = Meteor`（`bm=2` add，`ix=190`，走太阳）**
⇒ 平均亮度 140–148，变化质心扫满整条。见 `recipes/日出东方.json`。

### 4. "单向推进"（日出 / 擦除 / 填充）没有原生效果 —— 用播放列表让边界走

| 原语 | 为什么不行 |
|---|---|
| `Sunrise`(104) | 同色镜像 `i` / `SEGLEN-1-i`，亮区恒在中点，只变亮不移动 |
| `Wipe`(3) | `prog` 0→32767→65535，**来回擦**，不是单向 |
| `Meteor`(76) | 只有 `1+SEGLEN/20`（5%）灯珠亮，拖尾拉长就不动 |

**正解**：K 幕播放列表，每幕把"已升起"的子段加长一截，交叠淡入：

```json
{"segments":[
  {"start":0,      "stop_pct":8.3,  "fx":0, "col":[[255,233,184]]},
  {"start_pct":8.3,"stop_pct":100,  "fx":0, "col":[[58,10,0]]}
]}
```

- `stop_pct` / `start_pct` 按百分比定位（`apply_recipe` 支持），**一份配方同时跑 70 颗与 490 颗**
- 两段首尾相接、无重叠 ⇒ R1 满足；段 id 大的在上层，所以"未升起"段必须从 `pct` 开始，
  写成 `0..100` 会把整条盖住（实测退化成整条余烬）
- 验收：`verify_shape.py` 右边界增长 ≥25% 屏宽（实测 58%–91%）
### 5. 逐颗灌满（日出）的正解是 `Loading`(47)，不是播放列表

`mode_loading()` 只有一行：`gradient_base(true)`。`gradient_base` 里
`pp = (counter * SEGLEN) >> 16`，`counter = strip.now * ((speed>>2)+1)`：
**`pp` 是整数、逐颗步进**，`sx=0` 时 65.5 秒走完整个 SEGLEN —— 这正是"一颗 IC 一颗 IC 往前走"。

| 做法 | 逐颗? | 资源 | 下发 |
|---|---|---|---|
| **`Loading`(47) `sx=0`** | **是（整数 pp）** | 1 段 1 效果 | 一次成功 |
| 12 幕播放列表（我之前做的） | 否，每幕跳 `N/12` 颗 | 12 个预设 | 慢、易残留 |
| `Sunrise`(104) | 否，亮区恒在中点 | — | — |

**参数以灯珠为单位，跨灯数必须换算**：
- `ix` 控制过渡宽度 `brd = ix/2`（注意 `1 + loading ? A : B` 这个优先级 bug 让 `loading` 永远走第一支）
- 70 颗实测：`ix=120` → 过渡区 86%，`verify_shape` 峰值漂移 75%，合格
- **490 颗：同样 `ix` 下移动带只占 3%–24%，肉眼和峰值都测不出（已知限制，未解决）**
  ⇒ 跨灯数不能只线性缩 `ix`，需要"移动带占屏宽百分比"这个参数，下一版做
- `c1`（Shimmer 的带宽）同理，也是灯珠单位
### 6. `sx` 在不同效果里语义完全不同 —— 通用限幅会毁掉它

| 效果 | `sx` 含义 | `sx=0` 是什么 |
|---|---|---|
| `Sunrise`(104) | 日出时长（分钟） | 静止的太阳 |
| `Meteor`(76) | 速度 `counter=now*((sx>>2)+8)` | 最慢（≈8.2s 一圈） |
| `Loading`(47) | 填充速度 `counter=now*((sx>>2)+1)` | **最慢（65.5s 灌满整条）** |
| 普通效果 | 速度 | 会被防频闪限幅到 50 |

默认的防频闪限幅把 `sx` 钳到 50–90，对上面三个效果等于把"慢动作"改成"快放"。
现在 `_EFFECT_AXIS_EXEMPT` 已包含 47/76/104。**新效果先查 `FX.cpp` 里 `sx` 的用法，
再决定是否加豁免**，不要默认钳。

### 7. `verify_shape` 认两种"在动"，别用同一条标准

| 类型 | 特征 | 例 |
|---|---|---|
| **推进型**（填充变长） | 宽度变化明显 | 日出灌满 |
| **移动型**（亮带平移） | 宽度不变、位置在走 | 流星、扫描 |

所以判定是「右边界增长**或**峰值漂移 ≥25%」，只有"宽度和位置都不变"才判死。
早先把"宽度必须变"写死，把合法的移动型误判成"整条同亮同灭"。
